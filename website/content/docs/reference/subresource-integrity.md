# Subresource Integrity (SRI) for CDN Consumers

> `vellar-sdk` is published to npm and can be loaded straight from a CDN like
> unpkg or jsdelivr instead of bundling it. This page covers how to verify
> that CDN-served copy against tampering using Subresource Integrity.

By the end of this page you will know why a CDN-loaded SDK needs SRI, how to
get the right hash for the version you're loading, and how to use it in a
`<script>` tag or an `import` map.

## Prerequisites

- Loading `vellar-sdk` via `<script>` or an import map, not via a bundler
  (bundled consumers get integrity for free from their own lockfile/package
  manager, and do not need this page)

## Why this matters

A CDN is not the npm registry: it is a separate operator, with its own cache,
its own edge nodes, and its own opportunity to serve something other than what
was published. `npm publish --provenance` (used for every `vellar-sdk`
release) attests that a given tarball came from a specific commit and CI
run, but that attestation lives on npm's registry, not on unpkg's or
jsdelivr's CDN response. A `<script src="https://unpkg.com/vellar-sdk">` tag
with no `integrity` attribute trusts the CDN unconditionally: if it is
compromised, or serves a stale/tampered copy from a misconfigured cache, the
browser executes whatever came back.

[Subresource Integrity](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)
closes that gap: the browser hashes what it actually received and refuses to
execute it if the hash doesn't match what you specified up front.

## Getting the hash

Every published release records a `sha384` SRI hash for each file in `dist/`
in `dist/sri-hashes.json`, generated by `scripts/generate-sri-hashes.mjs` as
part of the release process (`.github/workflows/publish.yml`) and published
alongside the GitHub release notes for that version.

Fetch it directly from the CDN for the version you're loading:

```sh
curl https://unpkg.com/vellar-sdk@0.6.2/dist/sri-hashes.json
```

```json
{
  "index.js": "sha384-<...>",
  "index.cjs": "sha384-<...>",
  "x402-guards.js": "sha384-<...>"
}
```

Match the key to the file you're actually loading (`index.js` for the main
ESM entry point, `x402-guards.js` for the `vellar-sdk/x402-guards` subpath,
and so on, see the [license and versioning](./license.md) page for the full
export map).

You can also recompute it yourself without fetching anything, since SRI is
just a hash of the bytes:

```sh
curl -s https://unpkg.com/vellar-sdk@0.6.2/dist/index.js | \
  openssl dgst -sha384 -binary | openssl base64 -A
```

The output (without the `sha384-` prefix, which you add yourself) should
match the corresponding entry in `sri-hashes.json`. If it doesn't, stop:
either the CDN is serving something that isn't the published release, or the
`sri-hashes.json` you fetched is for a different version than the file you
hashed.

## Using it

```html
<script
  type="module"
  src="https://unpkg.com/vellar-sdk@0.6.2/dist/index.js"
  integrity="sha384-<the-hash-from-sri-hashes.json>"
  crossorigin="anonymous"
></script>
```

`crossorigin="anonymous"` is required alongside `integrity` for a
cross-origin `<script>`, without it, the browser won't even attempt the
integrity check and silently falls back to trusting the response.

An import map works the same way, pinning both the URL and the hash per
specifier:

```html
<script type="importmap">
  {
    "imports": {
      "vellar-sdk": "https://unpkg.com/vellar-sdk@0.6.2/dist/index.js"
    },
    "integrity": {
      "https://unpkg.com/vellar-sdk@0.6.2/dist/index.js": "sha384-<the-hash>"
    }
  }
</script>
```

(Import map integrity metadata is a newer addition to the spec; check your
target browsers' support before relying on it instead of the `<script>` tag
form above.)

## Pin the exact version

Always pin an exact version (`vellar-sdk@0.6.2`), never a range (`@^0.6.0`)
or `@latest`, when loading from a CDN with SRI. The hash is tied to one
specific build; a version range can resolve to a different file entirely on
a later page load, and the integrity check will then correctly, but
unhelpfully, refuse to execute anything at all.
